# 트러블슈팅 보고서

출처: 사용자가 제공한 [작업 로그](work-log.md) 11절. 아래 과정은 사용자 기록을 정리한 것이며 Codex가 서버에서 다시 재현한 결과는 아닙니다.

후속 성공 근거: [2026-09-09 터미널 원본](screenshots/06-localhost-test.png)에서 Nginx active, 내부 GET HTTP/1.1 200 및 페이지 본문, IPv4 외부 HTTPS HEAD HTTP/2 200을 확인했습니다. 이 화면은 성공한 후속 검증이며 최초 지연 자체의 재현 로그는 아닙니다.

## 사례 1 — 외부 HTTPS 응답 지연

| 단계 | 내용 |
|---|---|
| 증상 | EC2에서 `curl https://example.com` 실행 시 응답이 바로 출력되지 않아 사용자가 중단함 |
| 가설 | IPv6 연결 경로나 주소 선택 문제, 일시적인 상대 서버/네트워크 지연 등 가능성 |
| 검증 | `ping -c 4 8.8.8.8`에서 4개 송수신·손실 0%; `getent hosts example.com`에서 IPv6 주소 반환; `curl -4 https://example.com`에서 Example Domain 응답 |
| 조치 | 실습의 IPv4 아웃바운드 확인에 `curl -4`를 사용 |
| 결과 | IPv4를 이용한 외부 HTTPS 통신 성공. 패키지 목록 다운로드와 Nginx 설치도 사용자 로그에서 성공 |
| 재발 방지 | IPv4 환경에서는 진단 명령에 `-4`와 시간 제한을 넣고, 일반 요청과 주소별 요청의 로그를 함께 수집. 원인 입증 없이 보안 그룹 전체 포트를 추가 개방하지 않음 |

### 원인 판단의 한계

IPv6 주소가 조회됐다는 사실과 IPv4 강제 요청 성공만으로 최초 지연 원인을 IPv6로 확정할 수 없습니다. 원래 curl의 상세 로그·종료 코드·IPv6 경로 정보가 없기 때문입니다. `-4`는 확인된 우회 방법이며 일반 요청 지연의 근본 해결까지 입증한 것은 아닙니다.

### 참고 재현 명령 (실습 종료 후 서버 없음)

```bash
curl -v --connect-timeout 5 --max-time 20 https://example.com
curl -4 -v --connect-timeout 5 --max-time 20 https://example.com
curl -6 -v --connect-timeout 5 --max-time 20 https://example.com
ip -6 route
```

각 명령의 실행 시각·응답·종료 코드를 비교합니다. IPv6를 구성하지 않은 환경에서는 IPv6 요청 실패 자체가 웹 서비스의 IPv4 접속 실패를 의미하지 않습니다.

## 별도 관찰 — 콘솔 하단 액세스 거부

EC2 캡처의 인스턴스 경보 상태·서비스 상태 패널에 액세스 거부가 표시됩니다. 인스턴스 행은 실행 중이며 별도의 브라우저 화면에서는 웹 접속 성공이 확인됩니다. 거부된 정확한 API·정책은 제공되지 않아 원인을 확정하지 않았습니다. 이 표시만으로 관리자 전체 권한을 추가할 이유는 없습니다. 필수 EC2 작업이 실패할 때 해당 오류의 API와 필요한 리소스 범위를 확인합니다.

## 별도 관찰 — EC2 내부에서 SSH 재시도 시 개인키 경고

터미널 원본에는 이미 Ubuntu에 접속한 상태에서 `ssh -i ~/mission-key.pem ubuntu@43.201.48.130`을 실행하여 `/home/ubuntu/mission-key.pem`을 찾지 못한 경고가 있습니다. 이 위치의 `~`는 Mac 홈이 아니라 EC2 사용자의 홈입니다. Mac에서 시작하는 SSH 접속 명령과 EC2 안에서 실행하는 검증 명령을 구분합니다. 이후 같은 Ubuntu 프롬프트에서 Nginx active 및 내부·외부 HTTP 성공이 확인되므로 이 경고를 웹 서버 검증 실패로 처리하지 않습니다. 개인키를 EC2로 복사할 필요는 없습니다.
