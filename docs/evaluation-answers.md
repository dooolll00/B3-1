# B3-1 평가문항 답변

제공한 평가문항 사진의 항목 1~5 순서로 정리한 발표 참고 문서입니다. 답변은 이번 실습의 작업 기록과 증빙에 맞췄습니다. **현재 서버와 실습 네트워크는 삭제된 상태**이므로 실행·접속 성공은 종료 전 결과입니다. 항목 4는 실제 수행 이력이 아닌 가정 상황에 대한 대응 설명입니다. 최종 PASS/FAIL은 평가자가 판단합니다.

## 항목 1 — 구성과 동작 확인

### 1-1. VPC·Public Subnet·IGW·Route Table이 구성되어 있는가?

> 네. 서울 리전에 mission-vpc를 만들고, 그 안에 mission-public-subnet을 구성했습니다. mission-igw를 VPC에 연결했으며, 서브넷에 연결한 mission-public-rt에 0.0.0.0/0 → IGW 경로를 설정했습니다.

| 요소 | 이번 실습 값 |
|---|---|
| VPC | mission-vpc / 10.0.0.0/16 |
| Public Subnet | mission-public-subnet / 10.0.1.0/24 / ap-northeast-2a |
| IGW | mission-igw / igw-00282b3ebdefbbd81 |
| Route Table | mission-public-rt / rtb-0993a814677ceaebd |

근거: [라우팅·서브넷 연결 화면](screenshots/03-route-table.png), [최초 작업 기록](work-log.md).

### 1-2. EC2에 SSH 접속이 가능하고 웹 서버가 실행 중인가?

> 실습 당시 Mac에서 mission-key 개인키로 Ubuntu EC2에 SSH 접속했습니다. 서버 안에서 Nginx가 active인 것을 확인했고, localhost 요청도 HTTP 200과 웹 페이지 본문을 반환했습니다. 지금은 실습 종료 후 EC2를 삭제한 상태입니다.

실습 인스턴스는 `i-0636b2e10b12c0414`, 유형은 `t3.micro`입니다. 최초 SSH 접속은 작업 기록 기준이고, 터미널 사진에는 접속한 Ubuntu 프롬프트와 Nginx·curl 성공이 남아 있습니다.

근거: [터미널 검증](screenshots/06-localhost-test.png), [재개 당시 EC2 실행·3/3 통과](screenshots/05-ec2-running-2026-10-09.png).

### 1-3. 필요한 포트만 허용하고 SSH는 특정 IP로 제한했는가?

> 네. 웹 접속용 HTTP 80번은 모든 IPv4 주소에 공개하고, 관리용 SSH 22번은 제 IPv4 주소 하나만 허용했습니다. 모든 포트를 인터넷 전체에 공개하는 규칙은 만들지 않았습니다.

- HTTP: TCP 80 / `0.0.0.0/0`
- SSH: TCP 22 / 학습자 IPv4 `/32`
- SSH 허용 주소는 캡처 당시 설정이며, 인바운드 규칙은 두 개입니다.

근거: [보안 그룹 규칙](screenshots/04-security-group.png).

### 1-4. 외부 접속을 A/B 중 하나로 검증했는가?

> A 방식인 브라우저 접속을 선택했습니다. 2026년 10월 9일 종료 전에 http://3.35.53.2/로 접속했고, Hello Cloud Mission과 AWS EC2 + VPC + Nginx 문구가 정상 표시됐습니다.

최초 실습 주소는 `43.201.48.130`이며 재개 후 공개 IP가 바뀌었습니다. A 방식을 선택했으므로 B 방식의 `/health`는 구현하지 않았습니다.

근거: [외부 브라우저 접속](screenshots/07-external-access-2026-10-09.png), [README](../README.md).

### 1-5. EC2·EBS·EIP·IGW·VPC 정리를 확인할 수 있는가?

> 네. EC2는 Stop이 아니라 Terminated를 확인했습니다. EBS는 서울 리전의 전체 목록이 비어 있었고, Elastic IP는 할당된 주소가 없었습니다. IGW는 VPC에서 분리한 뒤 삭제했고 실습 VPC도 삭제했습니다.

## 항목 2 — 구현 방법 설명

### 2-1. 외부 → IGW → Subnet → EC2 흐름을 설명할 수 있는가?

> 사용자가 EC2의 공개 IP로 HTTP 요청을 보내면 IGW를 통해 VPC 안의 EC2에 도달합니다. EC2는 Public Subnet에 있고, 보안 그룹에서 80번 포트를 허용하므로 Nginx가 요청을 처리하고 응답합니다. 서브넷의 기본 경로는 인터넷으로 향하는 통신과 응답이 나갈 경로를 제공합니다.

[구성도](architecture.png)를 가리키며 사용자 → 인터넷 → IGW → Public Subnet의 EC2 → Nginx 순서로 설명합니다. 라우팅 테이블과 보안 그룹은 트래픽이 적용받는 설정이며 별도의 중계 서버는 아닙니다.

### 2-2. 보안 그룹 규칙을 어떤 기준으로 최소화했는가?

> 서비스에 필요한 포트와 서버 관리에 필요한 포트를 구분했습니다. 사용자가 웹 페이지를 볼 때 필요한 80번만 공개하고, 서버에 명령을 실행하는 SSH 22번은 제 IP로 제한했습니다. 이번 실습에서 사용하지 않는 DB 포트나 전체 포트 공개 규칙은 추가하지 않았습니다.

아웃바운드 전체 허용과 인바운드 전체 포트 공개는 서로 다른 설정입니다. 이번 실습은 인터넷 통신을 위한 아웃바운드를 허용하고 인바운드를 두 규칙으로 제한했습니다.

### 2-3. A/B 중 무엇을 선택했고 무엇을 구성했는가?

> A 방식을 선택했습니다. EC2에 공개 IPv4를 할당하고 IGW 연결과 기본 경로를 설정했습니다. 보안 그룹에서 HTTP 80을 허용한 다음 Nginx를 설치하고 사용자 페이지를 배포했습니다. 마지막에 외부 브라우저로 페이지가 표시되는지 확인했습니다.

배포 문구는 [HTML 재현본](../web/deployed-index.html)에 보관되어 있습니다. 이것은 사용자 로그를 바탕으로 만든 재현본이며 서버에서 내려받은 원본 파일은 아닙니다.

### 2-4. 실습 리소스를 어떤 기준으로 추적·정리했는가?

> mission-vpc, mission-web-server처럼 mission 이름을 사용했고, 작업 기록에 각 리소스 ID를 남겼습니다. 정리할 때는 이름만 보지 않고 ID를 대조했으며 체크리스트에 대상별 삭제 결과와 사진을 연결했습니다.

핵심 기준은 **이름 + 정확한 리소스 ID + 체크리스트**입니다. 별도의 관리 태그 체계를 구축했다고 설명하지 않습니다. 삭제 후 남은 기본 VPC와 다른 IGW는 이번 실습 대상이 아니므로 삭제하지 않았습니다.

## 항목 3 — 원리와 보안 이해

### 3-1. 0.0.0.0/0 → IGW 기본 경로가 필요한 이유는?

> VPC 내부 경로만 있으면 인터넷 목적지로 트래픽을 보낼 경로가 없습니다. 이번 실습은 외부 인터넷 통신과 웹 응답을 위해 기본 경로의 대상을 IGW로 지정했습니다. EC2의 공개 IPv4와 보안 그룹 설정도 함께 필요합니다.

`0.0.0.0/0`은 모든 IPv4 목적지에 대한 기본 경로입니다. VPC 내부 주소에는 더 구체적인 `10.0.0.0/16 → local` 경로가 적용됩니다. IGW로 가는 경로를 사용한다고 모든 포트가 자동으로 열리지는 않습니다. [AWS 라우팅 설명](https://docs.aws.amazon.com/vpc/latest/userguide/route-table-options.html)

### 3-2. Security Group과 IAM의 차이, 최소권한이 필요한 이유는?

> 보안 그룹은 서버로 들어오는 네트워크 통신을 제어하고, IAM은 AWS 리소스를 만들거나 변경하는 작업 권한을 제어합니다. 필요한 통신과 작업만 허용해야 계정이나 서버가 침해됐을 때 피해 범위를 줄일 수 있습니다.

이번 실습은 HTTP·SSH만 인바운드로 허용했습니다. 작업 기록상 별도 IAM 사용자 `mission-cloud-user`를 사용했고, 보관한 정책은 EC2/VPC/SG 관련 API와 서울 리전 조건을 포함합니다. S3/RDS 작업 권한과 관리자 전체 권한은 해당 실습 정책에 없습니다.

다만 `Resource: "*"`와 `ec2:Describe*`가 있어 자원·조회 범위를 더 제한할 여지가 있습니다. 모든 권한을 가장 좁게 제한했다고 주장하지 않습니다. 기본 버전 화면과 정책 JSON은 별도 근거이며 실제 기본 버전 본문/API 권한 시험은 수행하지 않았습니다. [실습 IAM 검토](../iam/README.md), [AWS 최소권한 설명](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies.html)

### 3-3. SSH나 DB 포트를 0.0.0.0/0으로 열면 안 되는 이유와 대안은?

> 관리용 포트를 모든 IP에 열면 인터넷의 누구나 접속 시도나 공격을 할 수 있습니다. SSH는 제 IP만 허용하고, DB가 필요한 구조라면 애플리케이션 서버에서만 접근하도록 제한하겠습니다.

이번에 실제 적용한 것은 SSH `/32` 제한입니다. DB는 만들지 않았습니다. DB 구성 시에는 공개 접근을 피하고 서버 보안 그룹을 소스로 지정하는 방법을 고려할 수 있으며, SSH 관리에는 VPN이나 Session Manager도 대안입니다. 이 대안들을 이번 실습에서 구현한 것은 아닙니다.

### 3-4. 가설 → 검증 순서를 유지한 이유와 로그 활용 방법은?

> 증상만 보고 설정을 바꾸면 원인을 잘못 판단할 수 있어서 가설을 세우고 검증했습니다. 이번에는 HTTPS 응답 지연에 대해 IPv6 경로나 일시적인 네트워크 지연을 의심했고, ping·DNS 조회·IPv4 강제 curl 결과를 비교했습니다.

작업 기록에는 ping 손실 0%, IPv6 DNS 주소, `curl -4`의 Example Domain 응답이 있습니다. 후속 터미널 사진에는 IPv4 HTTPS 200이 남아 있습니다. 이것으로 IPv4 통신 성공은 확인했지만, 원래 요청의 상세 로그가 없어 최초 지연 원인은 확정하지 않았습니다. [트러블슈팅 보고서](troubleshooting.md)

## 항목 4 — 가정 상황에 대한 대응

다음 답변은 이번에 직접 발생시켜 해결하거나 구축한 결과가 아닙니다. 현재 실습 구조를 바탕으로 한 점검·확장 계획입니다.

### 4-1. 외부 접속이 안 되면 어떤 순서로 점검하는가?

> 먼저 실습 서브넷이 올바른 라우팅 테이블을 사용하고 IGW 기본 경로가 활성인지 확인하겠습니다. 다음으로 보안 그룹의 80번 허용 규칙과 EC2에 연결된 보안 그룹을 확인합니다. 그다음 현재 공개 IP와 접속 주소를 대조하고, 서버 안에서 Nginx와 localhost 응답을 확인하겠습니다.

1. **라우팅:** 서브넷 연결, IGW의 VPC 연결, `0.0.0.0/0 → IGW` 상태 확인.
2. **SG:** HTTP TCP 80 허용 및 인스턴스에 연결된 SG 확인.
3. **공개 IP/DNS:** 재시작 후 IP 변경 여부 확인. 이번 실습은 IP로 접속하므로 사용자 도메인 DNS는 사용하지 않음.
4. **서버:** `systemctl is-active nginx`, `curl -i http://localhost`, 필요하면 `ss -lnt`로 80번 수신 확인.
5. **추가 근거:** Nginx 접근·오류 로그와 서비스 로그 확인. 내부는 성공하고 외부만 실패하면 NACL·OS 방화벽·접속 측 네트워크도 점검.

서버가 이미 삭제된 현재 상태에서 이전 주소가 열리지 않는 것은 정리 후 예상되는 결과입니다.

### 4-2. IAM 권한 부족으로 실패하면 필요한 최소 범위를 어떻게 찾는가?

> AdministratorAccess를 바로 추가하지 않고, 오류에 나온 실행 주체·거부된 작업·대상 리소스를 먼저 확인하겠습니다. 실제 실패한 API에 필요한 권한과 조건을 확인하고, 필요한 범위만 조정한 다음 같은 작업을 다시 검증하겠습니다.

오류 메시지와 가능한 경우 CloudTrail 기록을 확인합니다. 단순 Allow 누락인지, 서울 리전 조건 불일치인지, 다른 정책·권한 경계·조직 정책의 명시적 Deny인지 구분해야 합니다. 콘솔의 부가 패널 오류를 웹 서비스 실패로 단정하지 않습니다. 이번 기록의 콘솔 액세스 거부는 정확한 API를 확인하지 못했으므로 특정 권한 추가로 해결했다고 말하지 않습니다. [AWS AccessDenied 점검 안내](https://docs.aws.amazon.com/IAM/latest/UserGuide/troubleshoot_access-denied.html)

### 4-3. 트래픽 증가로 EC2를 두 대로 늘려야 한다면?

> 현재는 EC2 한 대가 모든 요청을 처리하므로 서버 자원이나 Nginx 처리가 병목이 될 수 있고, 한 대가 장애 나면 서비스도 중단됩니다. 실제 지표를 확인한 뒤 두 대의 EC2와 ALB를 구성해 요청을 분산하는 방법을 고려하겠습니다.

CPU·메모리·응답 시간·요청량을 확인해 병목을 판단합니다. 확장한다면 ALB용으로 서로 다른 두 가용 영역의 서브넷을 준비하고, EC2 두 대를 대상 그룹에 등록하며 리스너와 상태 검사를 설정합니다. EC2 웹 포트는 ALB의 보안 그룹에서 오는 요청을 허용하도록 바꾸고 사용자는 ALB 주소로 접속하게 합니다. 필요하면 Auto Scaling을 추가합니다.

ALB는 최소 두 가용 영역을 사용합니다. 이번에는 단일 서브넷·EC2 한 대만 구성했으며 ALB와 Auto Scaling은 만들지 않았습니다. 서버를 늘릴 때 세션·파일을 서버 로컬에만 저장하면 일관성 문제가 생길 수 있어 저장 방식도 검토해야 합니다. [AWS ALB 구성](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/application-load-balancers.html), [대상 그룹과 상태 검사](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-target-groups.html)

### 4-4. 예상하지 못한 비용이 나오면 무엇부터 추적·정리하는가?

> Billing에서 비용이 나온 서비스와 리전부터 확인하겠습니다. EC2 실행 시간, EBS 볼륨과 스냅샷, 공개 IPv4와 Elastic IP, NAT Gateway, 로드 밸런서, RDS 등을 확인하고 실습 리소스 ID와 대조하겠습니다. 필요한 증빙을 보관한 다음 사용하지 않는 자원을 정리하고 청구 내역을 다시 확인하겠습니다.

이번 실습에서는 서울 EBS gp3 비용 **USD 0.19**가 크레딧 **USD -0.19**로 상쇄된 내역을 확인했습니다. 정리 후 10월 예상 총계는 **USD 0.00**입니다. 비용 항목이 남아 있어도 과거 사용량일 수 있고, 0달러라도 크레딧 때문에 자원이 남아 있을 수 있으므로 목록 확인과 비용 확인을 함께 합니다.

NAT·로드 밸런서는 서울 빈 목록을 확인했고 RDS·스냅샷은 사용자 미생성 확인 기준입니다. 비용 반영 지연과 월 최종 청구액은 추후 재확인 대상입니다. [비용 상세](screenshots/12-billing-details-2026-10-09.png), [정리 후 청구서](screenshots/24-billing-after-cleanup-2026-10-09.png), [정리 체크리스트](cleanup-checklist.md)

## 항목 5 — 선택 보너스

> 이번 실습은 필수 과제인 네트워크 구성, 웹 배포, 접근 제어, 외부 접속 검증과 리소스 정리에 집중했습니다. HTTPS 인증서 적용과 Docker 배포는 구현하지 않았습니다.

외부 사이트로 보낸 HTTPS 요청 성공은 내 웹 서버에 HTTPS를 적용했다는 의미가 아닙니다. 보너스 수행 결과나 보너스 크레딧을 받았다고 설명하지 않습니다.
